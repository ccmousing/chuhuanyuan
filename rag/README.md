# 出花园民俗 · RAG 知识库与检索（baseline）

这是「出花园」民俗知识库 + 检索器的**第一阶段成果**。目标不是做出最漂亮的系统，
而是**先把链路跑通、用真实数据暴露问题**——`rag-plan.html` 里那个判断在这里得到验证：
RAG 项目失败大多不是因为模型笨，而是检索不到正确上下文。

## 目录

```
rag/
├── knowledge_base.json   结构化知识库（31 chunks / 6 篇 / 11 条来源）
├── retrieve.py           检索器：字二元组 + 单字回退 + BM25 + 地域加权
└── README.md             本文件
```

`knowledge_base.json` 由 `miniprogram/utils/content.js` **派生**（不是手抄的），
所以小程序里改正文，重跑一次派生脚本即可同步——内容只有一份源头。

## 怎么跑

```bash
# 需要 Python 3.8+，零第三方依赖
python rag/retrieve.py
```

会打印 10 个测试查询的命中情况，包含一个**超纲题**（「量子力学的基本原理」），
用来验证拒答是否生效。

## 知识库设计

| 维度 | 做法 | 理由 |
|---|---|---|
| 切块 | 按 `sections` 聚合，单 chunk 超 320 字按段落再拆 | 31 个 chunk 平均 152 字，粒度适合检索 |
| 来源 | 每个 chunk 带 `sources[]`，含标题 / URL / 类型（gov / media） | `rag-plan.html` 红线：**无来源不收录**。本次 11 条来源中 8 条来自政府或官方媒体 |
| 地域 | 每个 chunk 带 `regions[]`（general / shantou / chaozhou / jieyang / overseas） | 潮汕三地对同一问题答案不同 → 把「内容有多个正确答案」转成「检索问题」，见 `rag-plan.html` 图 2 |
| 审校标记 | `needVerify` 标记含各地差异较大的礼俗细节 | 25/31 个 chunk 带此标记，回答时须标注「各地略有差异」 |

## ⭐ Baseline 阶段实测发现并修掉的 3 个缺陷

这一段比代码本身更值得看——**每个都是先跑数据才发现、且不跑数据永远发现不了的**。

### 缺陷 1：功能词把超纲题顶上高分（最严重）

第一版跑出来，「量子力学的基本原理是什么？」**高分命中**了 `twelve-flowers#s1`（5.4 分）。

原因：查询里的「是什」「什么」这类功能词，和文档里的同义词撞上。小数据集（31 chunks）里
BM25 的 idf 区分度不够，压不住它们。

**后果**：如果直接接 LLM，系统会对任何问题都「检索到东西」然后硬答 → 永远不拒答 → 幻觉率爆表。

**修法**：① 停用词表（多字词先删、单字再删，**顺序不能反**）；② 增加**覆盖率兜底**——
查询实词中至少 50% 出现在命中 chunk 里，否则判定为「没检索到」。

> 教训：**「拒答」不是加一句提示词就能做到的，它依赖检索层真的能区分相关与不相关。**

### 缺陷 2：bigram 粒度太粗，误命中跨主题文档

修完停用词后，「出花园要穿什么鞋？」的 top1 变成了 `gongpopo#s1`（讲公婆母的）——错了。

原因：「穿鞋」这个二元组在文档里没恰好出现（文档写「穿着红木屐」），
于是唯一得分的是「花园」——而它在 31 个 chunk 里几乎无处不在，idf 极低却 tf 很高。

**修法**：**单字回退**。除二元组外，同时索引单字（加 `_` 前缀独立统计 df/idf），
打分时权重打 0.55 折。召回上来了，精度靠折扣和覆盖率兜住。

修正后 top1 变成 `why-clogs#s4`（今天的木屐）✅。

### 缺陷 3：词汇鸿沟（**未修，是下一步的理由**）

「出花园要买什么食材？」的 top1 是 `what-is#s4`（这一天大致要做什么），
而理想答案是 `head-dish`（头彩食十二碗）。

原因：知识库里用的是「菜品」「彩头」，查询用的是「食材」——**字面完全不重叠**。
这是词匹配方法的固有局限，单字回退也救不了（「食」字两边都有，但「材」字只在查询里）。

**这正是值得上向量检索的实证理由**：语义相近但用词不同的 query-document 对，
只有 embedding 能拉近。这条可以直接写进评估报告——
「先用 baseline 量化了词匹配的天花板，再决定是否值得引入向量检索」，比一上来就说「我要用 RAG」有说服力。

## 当前 baseline 的实测表现

| 查询 | top1 命中 | 判定 |
|---|---|---|
| 出花园要穿什么鞋 | `why-clogs#s4` 今天的木屐 | ✅ 正确文章 |
| 十二花水有哪些花 | `twelve-flowers#s1` | ✅ |
| 咬鸡头是什么寓意 | `head-dish#s2` | ✅ |
| 潮州和揭阳有什么不同 | `three-cities#s3` 潮州篇 | ✅ |
| 孩子几岁出花园 | `what-is#s2` | ✅ |
| 公婆母是谁 | `gongpopo#s2` | ✅ |
| 为什么要拜公婆母 | `what-is#s4`（流程节） | ⚠️ 可接受，`gongpopo` 专篇更理想 |
| 出花园要买什么食材 | `what-is#s4` | ❌ 词汇鸿沟，理想是 `head-dish` |
| **量子力学的基本原理** | 无有效命中（cover 0.20） | ✅ **正确拒答** |
| 出花园汕头怎么办 | `three-cities#s2` 汕头篇 | ✅ 地域加权生效 |

**统计**：10 例中 7 例 top1 完全正确、2 例可接受/次优、1 例错误、1 例超纲正确拒答。

> 这只是 10 个手选查询，**不是评估**。真正的评估要按 `rag-plan.html` 第 7 章做：
> 固定 20 题（含 5 道超纲题测拒答）、对照组（本方案 vs 直接问大模型）、
> 四项指标（引用准确率 / 拒答正确率 / 幻觉率 / 三地一致性）。

## 下一步

1. **接 LLM**：`retrieve.py` 已就绪，只需加一个 OpenAI 兼容客户端
   （DeepSeek / 硅基流动均可），Key 从环境变量读，**不写进代码**。
   Prompt 必须包含：强制引用 chunk id、检索不到就说「不知道」、needVerify 内容标注地域差异。
2. **建 20 题评估集**：从 `quiz-bank.js` 的 30 题里选 15 题作问答题，
   再加 5 道超纲题。这是唯一能证明「RAG 比直接问大模型好」的东西。
3. **可选：向量检索对照**。先用 baseline 数据说明词匹配的天花板，再决定是否引入。
4. **内容审校（A7）**：25/31 个 chunk 带 `needVerify`，上线前必须过民俗专家。
