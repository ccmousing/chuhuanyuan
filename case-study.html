项目概览

一句话说清：问题是什么、我做了什么、产出了什么。

问题

「出花园」是潮汕独有的成人礼俗（2018 年入选广东省省级非遗），但它只活在长辈的口述里和每年一次的线下活动里——在外潮汕青年与海外潮籍后代几乎没有可自主查询、可参与的数字入口。

做法

不做一个「科普展示页」，而是把知识、互动、服务、情感留存串成一条完整链路：文化科普馆 + 仪式体验馆 + 服务预约 + 内容社区，并用内容分级同时服务游客、研学学生、本地家长三类人群。

产物

一份 7 章策划方案（含 4 张架构图）、一套 7 屏可点击高保真原型、一份 RAG 民俗问答技术方案、一份完整内容包清单。全部离线可打开、无外部依赖。

背景：为什么这个项目值得做

四个已核实的事实，构成了立项的依据。

2018入选广东省第七批省级非物质文化遗产名录（2014 年先入汕头市级）
3000万全球海外潮人规模，构成强烈的情感连接需求
10届+揭阳榕城自 2015 年起连续举办集体成人礼的届数
8万揭阳榕城线上活动平台单次点击量量级，已验证线上需求
结论：汕潮揭三地官方已连续多年举办集体成人礼，并各自沉淀出线上化经验，但尚无以「出花园」为单一主题、面向三类用户、可持续日常运营的独立产品。需求、素材、权威背书三者齐备，缺的是产品化的整合。

三个核心洞察

它们直接决定了产品形态，而不是凭空做功能堆砌。

洞察一：三类用户的诉求几乎不重叠，必须分层，而不是折中

游客要「30 秒看懂」、学生要「能闯关能带走」、家长要「流程、清单、能约到人」。用一个通用页面服务三类人，结果是三类人都留不住。方案给出的解法是一套内容库 + 三个阅读层级，而不是维护三套内容。

洞察二：这个民俗的情感高点，恰好是产品唯一的传播支点

用户旅程中情绪从「好奇」抬升到「投入·感动」再到「自豪·认同」，而情绪最高点正出现在仪式走完、纪念证书生成的那一刻。把分享钩子布置在这个位置，转化效率最高——这也是 MVP 必须包含「祝福卡 + 纪念证书」的原因。

洞察三：非遗类内容的最大风险不是没人看，而是「讲错了」

「出花园」各地细节差异极大（十二种花草名目、十二碗菜品、择吉月份），网络流传版本互相矛盾。因此方案把内容准确性当作产品功能来设计：统一标注地域来源与「需进一步核实」，并规划了文化馆/民俗专家审校环节，以及能溯源引用的 RAG 问答。

三个关键设计决策

面试和答辩最容易被追问的就是这些「为什么」，先想清楚。

为什么是综合平台，不是纯科普？
理由纯科普做完就死——用户看完即走，没有回访理由，也没有可持续的内容供给动力。
取舍综合平台成本更高，因此用三期演进化解：MVP 只做「科普 + 互动 + 分享」，服务与社区放到 V2。
为什么内容分级用「一套库三层展开」，不做三套？
理由同一条知识给「摘要 / 标准 / 深读」三段文本，按身份默认展开层级。内容维护成本只增加约 40%，而不是 3 倍。
取舍长文本编写要求更高，需要一次就把三层写全；换来的是后续零重复维护。
为什么 MVP 只做 3 个页面？
理由MVP 阶段唯一目标是验证内容吸引力，任何非核心功能都会稀释验证信号。
取舍明确列了「低价值高成本 → 暂不做」清单（3D/AR 仪式还原、自建短视频平台、积分商城），主动克制。

技术方案

重点说清「我做了什么技术判断」，而不只是「我用了什么」。

7.1　前端：用原型本身质疑信息架构

原型不是「画着好看」，而是用来验证结构：把 7 屏真的用 HTML/CSS/JS 做出来、点得通， 才能暴露问题——例如「非 Tab 页面进入后底部导航失去高亮」这类体验断裂，只在真机点一遍才会发现。 全部使用原生技术 + 内联 SVG，零外部依赖、离线可打开，方便投屏演示与分发给合作方。

7.2　RAG：为什么这个地方需要检索，而不是直接问大模型

直接问通用大模型「出花园的十二种花是什么」，它会给出一个「很像」但可能错误或张冠李戴的答案—— 而地方民俗恰恰各地版本不同、网络资料互相矛盾。 所以我设计的是一条「先检索本地方知识库、再生成、且必须带引用来源」的链路： 答案里每一处事实都能指回知识库中的具体条目和它的地域来源，这也让「文化准确性」从一个宣传口号变成了可测量的技术指标。

核心设计

  • 结构化优先：知识库不是原始网页切块，而是带字段的结构化条目
  • 地域差异作为一等公民：同一条知识点可挂多个地域版本，检索时按用户所在地域优先
  • 强制引用：生成结果必须返回引用条目 ID，无引用则降级为「未找到」

技术选型倾向

  • Embedding：中文语义表现好的多语模型（如 BGE-M3 类）
  • 向量库：本地 Chroma 起步，数据量小、无需运维
  • 生成：OpenAI 兼容接口（可对接 DeepSeek / 硅基流动），用 requests 直调，不用框架黑盒
  • 进阶：用 LangGraph 包成「检索 → 生成 → 自检引用」三节点

可量化验证

  • 建 20 条测试问题集（含地域差异、易混淆、超纲三类）
  • 指标：检索命中率 / 引用准确率 / 幻觉率（答案中无法溯源的事实比例）
  • 基线对比：直接问通用大模型 vs 本方案，用同一套题目跑对照
为什么这条技术线值得写进简历：它把一个文化项目变成了一个有明确对照实验和指标的 RAG 实践—— 既有业务语境（非遗内容准确性），又有工程判断（结构化 vs 切块、地域元数据、强制引用）， 还有可复现的评估方法。这正是 AI 应用岗位最想看的东西。 完整的六步实施清单与技术选型对比见 RAG 方案 →

指标设计（目标假设 · 非实测结果）

项目尚未上线，以下全部是「用来判断做对了没有」的假设，不是成绩。

指标分三层：认知 → 参与 → 传播，与用户旅程一一对应。
层级指标目标假设为什么选它
认知分享卡片打开率≥ 25%衡量「内容是否让人愿意点开」，是最上游的漏斗口
认知「出花园是什么」完读率≥ 55%验证三屏讲清定义的表达是否成立
参与七步仪式走完率≥ 40%核心互动功能的真实吸引力
参与预约咨询转化可追踪率≥ 30%验证家长侧工具属性是否成立
传播单用户带来分享次数≥ 1低于 1 意味着没有自然增长，产品不成立
传播老带新占比≥ 20%决定获客成本能否长期成立
诚实声明：上述为设计阶段的目标假设，本项目尚未上线运营，无任何实测数据。对外演示时须明确说明，避免被误读为项目成绩。

复盘与下一步

主动说不足，比等别人指出更可信。

做对了什么

  • 先核实事实再设计，避免了「网上抄来的民俗」这类硬伤
  • 用功能分层图明确「每期不做什么」，克制住了首版堆功能
  • 把原型做成可点击的，而不是静态稿——结构问题因此暴露

如果重来会怎么改

  • 应该在需求阶段就更早锁定「是否要真上线」，避免后期方案范围反复
  • 内容分级的三层文本应同步编写，否则后续补写成本会叠加
  • 原型阶段可以更早引入真实用户（本地家庭）做一次可用性走查
