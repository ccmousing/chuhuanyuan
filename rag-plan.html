技术方案 · RAG

让「出花园」问答不编造、可溯源

地方民俗最大的特点是各地版本不同、网络资料互相矛盾——直接问通用大模型，它会给出一个「很像」但可能张冠李戴的答案。 本方案把方案站第 2 章的民俗知识做成结构化知识库，检索后再生成，每一处事实都能指回具体条目及其地域来源。

为什么这个地方必须用检索

不是为了炫技。先说清「不用 RAG 会出什么问题」。

痛点一：事实细碎且易错

「十二花水」到底是哪十二种花、「头彩食」十二碗分别是什么——大模型训练语料里这类长尾民俗信息稀薄，很容易生成一个似是而非的清单。

痛点二：同一个问题有多个正确答案

汕潮揭三地做法不同，甲子等地区还有自己的版本。模型无法知道提问者要看哪个版本，往往把三地做法混在一起讲。

痛点三：错了没人知道

通用问答没有出处。用户无法判断这句话来自权威资料还是模型脑补，而文化传播一旦出错，损害的是整个项目的公信力。

一句话方案：把「可核验」当作产品功能来设计——先检索本地知识库，再让模型基于检索到的条目作答，并强制返回引用； 检索不到就明确回答「知识库中暂无此信息」，而不是推测。这样「文化准确性」从一个宣传口号，变成了一个可测量的技术指标。

1.1　和「直接把资料塞进提示词」有什么区别

做法优点为什么不选 / 何时可选
全部塞进长上下文实现最简单，无需向量库知识库一旦超过几千字就开始吃 token 与成本；且无法给出「这句话来自哪条」的稳定引用 ID。仅在原型验证阶段可用。
关键词检索零依赖、结果可解释用户会说「十五岁那个仪式是干嘛的」，不会说「出花园」。口语化提问命中率低。数据量极小（<50 条）时可作为对照基线。
向量检索（本方案）能处理语义相近与口语化表达；元数据可参与过滤与排序需要一次向量化成本与一个向量库，但可本地持久化、无需运维。
直接问通用大模型零成本起步不保留此处——它不会被淘汰，而是留作对照组，用来证明本方案真的更好。

知识库设计

这是整个方案里最花心思的地方——知识怎么存，直接决定检索能有多准。

3.1　条目字段定义

字段类型说明与设计理由
idstring稳定唯一标识，如 ritual-step-05。引用溯源的基础，一旦发布不可变。
questionstring该条目对应的典型提问（可多条），用于向量化的主要文本。
answerstring条目正文。控制在 120–300 字，保证「一条 = 一个完整知识点」。
categoryenum由来 / 流程 / 符号 / 地域差异 / 现代演变 / 禁忌。用于检索后分层返回。
regionenum[]汕头 / 潮州 / 揭阳 / 甲子 / 海外 / 通用。核心设计点，见 3.3。
sourcestring来源，如「广东文明网 2026-08 报道」。生成答案时一并返回。
confidenceenumverified / needs_review。对应用户旅程里的准确性约束：needs_review 的条目在答案中必须带「需进一步核实」标注。
levelenumchild / teen / adult，对应方案站的「一套内容库三层展开」，可按用户身份优先返回合适深度。
variantsobject[]同一条知识点的其它地域版本，见 3.3。

示例条目（JSON）

{
  "id": "ritual-step-05",
  "question": ["出花园为什么要咬鸡头", "咬鸡头是什么意思", "头彩食有哪些菜"],
  "answer": "咬鸡头是出花园宴席上最具象征性的一环：整鸡上桌、鸡头朝向孩子，孩子象征性地咬一口，取「独占鳌头、出人头地」之意。同桌的十二碗「花园菜」每样都要吃一点，各有彩头——猪肚寓意「换肠肚」、芹菜勤劳、葱聪明、蒜会算、豆干做官。",
  "category": "流程",
  "region": ["通用"],
  "source": "中国文明网《「出花园」：儿童成人礼俗》",
  "confidence": "verified",
  "level": "teen",
  "variants": [
    { "region": "甲子", "note": "十二碗饭菜摆在大竹胡上，出花园者坐眠床上吃，男向内、女向外" }
  ]
}

3.2　知识从哪里来

  • 直接复用方案站第 2 章的「已核实事实清单」——它本身就是按「知识点 + 来源」整理的，转换成本极低。
  • 首批只做 60 条，覆盖：是什么 / 由来 / 七步流程 / 6 个文化符号 / 三地差异 / 海外传播。不追求全，追求每条都能溯源。
  • 不做原始网页切块。网页切块的边界由 HTML 决定，不由语义决定，会出现「半句话」条目，引用时也无法指认。人工整理 60 条的成本，远低于后期修补检索质量的成本。

3.3　地域差异怎么建模（本方案最关键的判断）

图 2　地域差异建模：把「各地不一样」这件麻烦事，从内容问题转成检索问题——用元数据解决，而不是靠模型猜。
为什么这是本方案最重要的判断：多数 RAG 项目的失败不是因为检索不准，而是因为知识本身有多个互相冲突的正确答案，系统却只能给出一个。 把地域做成一等元数据后，同一个问题可以正确地返回不同版本的答案，并且每个版本都能指认来源。

六步实施清单

每步都有可验收的产出，做不完这一步就不进下一步。

步骤任务具体要做的事验收标准
1建知识库 从方案站第 2 章拆出 60 条结构化条目，补齐 question / answer / category / region / source / confidence 字段。 60 条全部有 source；无 source 的条目一律标 needs_review。
2元数据校验 人工过一遍 region 与 confidence，把三地差异点单独抽出来做 variants。 差异型知识点（≥8 条）都有 variants 字段。
3向量化入库 对 question + answer 做向量化，写入 Chroma 并持久化到本地目录；元数据一并存入。 重启脚本后无需重新入库即可检索（持久化生效）。
4最小问答链路 检索 Top-5 → 组装提示词（明确「只许依据材料作答」）→ 调生成模型 → 打印答案 + 引用条目 ID。 问 5 个问题，输出中能看到引用 ID。
5引用校验与拒答 校验生成内容是否引用了真实存在的条目；不通过则返回「知识库中暂无此信息」。 编造一个知识库里没有的民俗问题，系统正确拒答。
6评估与调优 用 20 题测试集跑对照实验（本方案 vs 直接问大模型），调 Top-K 与提示词。 产出评估表：四个指标 + 与基线的对比。
顺序很重要：不要先写代码。第 1、2 步（知识库与元数据）是决定上限的工作，也是最容易被跳过的工作。 很多 RAG 项目效果差，问题不在模型或向量库，而在知识本身没整理干净。

技术选型

每组都给推荐 + 理由，也写清「什么情况下该换」。

5.1　Embedding 模型

选项倾向理由
BGE-M3 类中文多语模型推荐中文语义表现好，支持多语言（对海外潮人场景有用），可通过国内平台直连调用，成本可控。
通用英文为主的 Embedding备选便宜且生态好，但中文长尾民俗词的语义区分度弱，容易出现「把不同知识点混在一起」。
本地部署小模型暂不零调用成本，但要处理环境与显存；等数据量涨到几千条、调用成本显著时再考虑。

5.2　向量库

选项倾向理由
Chroma（本地持久化）推荐Python 原生、单文件目录、零运维，天然支持元数据字段过滤——正好匹配本方案「地域元数据参与检索」的核心设计。
FAISS备选检索快、依赖轻，但元数据要自己维护一套映射，对本方案的地域过滤不友好。
云托管向量库暂不60 条数据用云服务属于过度设计；等知识库上千条、需要多人协作时再迁移。

5.3　生成模型与调用方式

选项倾向理由
DeepSeek（OpenAI 兼容接口）推荐中文好、价格低，接口是 OpenAI 兼容格式，换模型只改 base_url 与 model 名。
千问（DashScope）备选国内直连稳定，适合作为对照实验的第二个生成模型。
直接用 requests 调 HTTP 接口推荐不套框架黑盒——中间的检索结果、提示词、返回内容都看得见，便于逐层排查与调优，也便于在面试里讲清每一步。
LangGraph 封装三节点进阶功能跑通后，可把「检索 → 生成 → 引用自检」包成三个节点，形成带条件分支的工作流（自检失败则回退重检索）。这时框架是加分项而不是依赖。

明确不选的东西

  • 不用框架全家桶做黑盒：面试会被追问中间过程，说不清就是减分。
  • 不做微调：60 条数据做微调必然过拟合，且成本远高于检索方案。
  • 不堆长上下文：成本高、无引用、无法定位错误来源。
  • 不做多模态：图鉴配图用人工编辑即可，不需要模型理解图片。

成本量级预估

  • 入库：60 条 × 约 200 字 = 1.2 万字，向量化一次性完成，成本可忽略。
  • 单次提问：检索结果 5 条约 1500 字 + 问题，单次生成成本以「厘」计。
  • 评估：20 题 × 2 组对照 = 40 次调用，完全在免费额度内可完成。
  • 结论：整个方案不需要任何付费基础设施即可完整跑通。

五个关键设计决策

答辩和面试最容易被追问的就是这些「为什么」，先想清楚。

  • 结构化条目，而不是原始网页切块。网页切块的边界由排版决定，会出现语义不完整的「半句话」；结构化条目的边界由知识点决定，且能给出稳定、可引用的 id。
  • 地域差异作为元数据，而不是靠提示词叮嘱模型「注意各地不一样」。提示词约束是不可靠的软约束；元数据过滤 + 排序是可靠的硬机制。
  • 强制引用，无引用则拒答。把「宁可说不知道，也不编」写成代码逻辑，而不是写在提示词里。拒答不是失败，是正确行为。
  • 追求「可核验」，而不是「像人在聊天」。民俗问答的价值在于准确与可追溯，不在于语气自然。答案默认附引用来源，让用户自己能判断。
  • 评估先行：先写 20 题测试集，再写第一行代码。没有测试集的 RAG 项目无法判断改动是变好还是变坏，最后只能凭感觉调参。

评估方法

这一章是让项目从「演示」变成「工程」的关键。

7.1　测试集设计（共 20 题，三类）

题型题量考察什么正确答案的判定
事实型8答案在知识库中且唯一。如「出花园什么时候入选省级非遗」「咬鸡头出自哪个传说」。与知识库条目一致，且引用 ID 正确。
差异型7同一问题存在多地不同答案。如「拜公婆母要准备什么供品」「十二花水是哪十二种」。返回与提问地域匹配的版本；未指定地域时说明存在多个版本而不是混答。
超纲型5知识库中确实没有答案。如「出花园要准备多少钱」「明年哪天办最好」。正确行为是拒答并引导查看科普内容，而不是给一个听起来合理的答案。

7.2　指标定义

指标定义为什么要单独测它
检索命中率 Recall@5正确条目是否出现在返回的前 5 条内定位问题出在「检索」还是「生成」——这是排查 RAG 的第一步
引用准确率答案标注的引用条目，是否真的支持该结论防「引用看起来有，但张冠李戴」——这是最隐蔽的错误
幻觉率答案中无法在知识库中溯源的陈述占比本方案的核心指标，直接对应用户最担心的问题
拒答正确率超纲题中正确拒答的比例拒答能力只有专门测才能测出来，否则会被「看起来更有用」的系统掩盖

7.3　对照实验设计

关键设计：一定要有对照组。同一套 20 题，分别喂给「本方案（检索 + 强制引用）」和「直接问通用大模型」， 人工或半自动标注四项指标，做成一张对比表。
只有存在对照，「我的方案更好」才是一个可以被质疑、也可以被验证的结论，而不是自我感觉。 这也是整个项目里最具说服力的一张表——尤其是幻觉率那一栏。
诚实预期：直接问大模型在「事实型」题目上可能表现并不差（因为核心事实语料充足）， 本方案的优势主要体现在差异型（多地版本）与超纲型（正确拒答），以及「可溯源」这一点上。 如实呈现这个结论，比宣称「全面碾压」更可信——也更像工程而不是营销。

怎么把它讲进简历与面试

技术做完了不等于讲得出来。这一节直接给你话术。

8.1　简历上怎么写（三句话）

「出花园」民俗知识库 RAG 问答　·　个人项目
① 问题：地方民俗资料网上互相矛盾，通用大模型问答易编造细节、无法溯源。
② 做法：整理 60 条带地域/来源/置信度元数据的结构化知识条目（Chroma 向量库）， 用 requests 直调 LLM 接口搭建「检索 → 生成 → 引用校验」链路，无法溯源时降级拒答。
③ 结果：构建 20 题三类测试集（事实/地域差异/超纲），与直接提问通用模型做对照， 幻觉率与拒答正确率显著优于基线。

写作要点：「问题 → 做法 → 结果」三段式，每句都有名词和数字，不写「负责」「参与」这类虚词。 第 ③ 句里的数字必须等评估跑完再填——写不出来的指标不要编。

8.2　最可能被问的 5 个问题

问题回答要点
为什么不用 LangChain 一把梭？先说结论：为了每一步都能看见和调优。中间检索结果、提示词、返回内容都可控，排查问题时不用猜框架内部做了什么。框架适合作为后期的封装层，不适合作为理解层。
为什么人工整理结构化条目，而不是直接切文档？切块的边界由排版决定，会出现语义不完整的条目；而引用溯源需要一个稳定的条目 ID。数量小（60 条）时手工整理的成本远低于后期修补检索质量的成本。
怎么防止模型乱编？三层：提示词层（只许依据材料）、机制层（强制返回引用 ID + 校验，无引用直接降级拒答）、评估层（单独统计幻觉率与拒答正确率）。重点是后两层，提示词是不可靠的软约束。
知识库数据量这么小，为什么要上向量库？诚实回答：数据量小的时候，关键词检索确实也能用。选向量库是因为要处理口语化提问与语义相近的表达，并且要为后续扩容留余地；同时把关键词检索作为基线一起评估，用数据决定。
这个项目你最大的收获是什么？答「上限由数据决定，而不是由模型决定」。一开始想直接调模型解决，后来发现瓶颈在知识本身——地域版本冲突、来源不明。把知识整理干净、把地域建成元数据之后，效果提升比换模型明显得多。

风险与边界

主动说清局限，比等别人指出更可信。

风险说明应对
知识库规模有限60 条只能覆盖核心知识点，冷门问题会频繁触发拒答，用户可能体感「不够聪明」。如实展示覆盖范围；对拒答结果给出「可查看哪一章节」的引导，把拒答变成导流而不是死路。
缺少权威审校知识条目来自公开报道整理，未经文化馆或民俗专家审校。把 confidence 字段与「需进一步核实」标注做进产品；对外统一说明数据来源；推动一次官方审校。
地域判定不准用户未说明地域时，系统只能给通用版本或列出多个版本。不强猜。未指定地域时显式提示「该问题各地做法不同，以下为通用/汕头版本」，允许用户切换。
引用校验过于严格可能把本来正确的答案也拦下来，导致拒答率偏高。把「无引用拒答」与「引用不足则加免责标注」分开处理，用测试集判断阈值，而不是一刀切。
版权与来源标注引用来源需准确、可核实，不得篡改或去署名。source 字段保存原文出处与时间；对外展示时保留来源名称；不确定来源的条目一律不收录。
